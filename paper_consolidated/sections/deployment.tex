\section{Deployment on Resource-Constrained Environments}
\label{sec:deployment}

% ----------------------------------------------------------------
\subsection{On-Device and Mobile Deployment}
\label{subsec:deployment_mobile}

On-device deployment removes the network round trip, the per-token charge, and the transmission of prompt content to a third party. It enables functionality in offline and low-bandwidth environments and is a precondition, though not on its own a guarantee, of a private personal assistant. The primary challenges are memory (RAM and storage), sustained inference throughput under thermal constraints, and battery impact.

\subsubsection{What ``On-Device'' Does and Does Not Guarantee}
\label{subsec:deployment_privacy_scope}

The claim that on-device inference means no data leaves the device is made
frequently, including in earlier drafts of this paper, and it is a property of
the \emph{application}, not of the model. Running weights locally establishes
only that the prompt is not transmitted to an inference API. Whether user data
leaves the device depends on four further things, none of which the model
controls: whether the application emits telemetry, crash reports, or analytics
that embed prompt content; whether it logs conversations to a cloud-synchronized
store or a backup; whether the pipeline escalates to a cloud model, in which case
the escalated calls are exactly the sensitive ones if routing is difficulty-based
rather than sensitivity-based; and whether other stages of the pipeline, such as
retrieval over a hosted index or a tool call to a remote API, transmit the same
content the local model was chosen to protect.

The correct statement is therefore conditional: on-device inference removes one
specific egress channel, and eliminates data egress only in an application whose
whole pipeline is local and whose telemetry is either absent or content-free.
Apple's design \citep{gunter2025afm} is instructive precisely because it treats
the escalation path as the hard part and builds Private Cloud Compute around it
rather than claiming the on-device model makes the question moot. Every privacy
claim in this paper should be read under this scope condition, including those in
Sections~\ref{sec:applications} and~\ref{subsec:discussion_implications}.

\subsubsection{Apple Intelligence (AFM)}

Apple's Foundation Models \citep{apple2024intelligence,gunter2025afm} are the most fully documented on-device \gls{slm} deployment. The 2025 report \citep{gunter2025afm} describes a $\sim$3B on-device model, optimized for Apple silicon through KV-cache sharing (dividing the model so the second block reuses the first block's cache, a reported 37.5\% memory saving) and 2-bit quantization-aware training, paired with a Parallel-Track Mixture-of-Experts server model on Private Cloud Compute. The on-device model is reported competitive with Qwen3-4B and Gemma-3-4B on its target tasks; the server model with Llama~4 Scout. The third-generation framework \citep{apple2026afm3} adds a natively multimodal, sparsely activated on-device model and opens the same API surface to third-party cloud models, so that an application calls the local \gls{slm} by default and escalates to a frontier \gls{llm} only on demand. Google's Gemini Nano and Samsung's Gauss \citep{samsung2023gauss} occupy the same design point on Android and Galaxy devices.

\subsubsection{Samsung Gauss}

Samsung Gauss \citep{samsung2023gauss} is a family of language models for Galaxy devices, including a ${\sim}1.7$B on-device model targeting the Gauss1 chip and Exynos 2400 \gls{npu}. Samsung reports that Gauss enables on-device email summarization, translation, and writing assistance without requiring internet connectivity.

\subsubsection{General Mobile Deployment Considerations}

\glspl{slm} targeting mobile deployment must navigate three constraints. (1) \emph{Memory}: Consumer smartphones typically provide 6--12~GB RAM, of which the OS uses 2--4~GB, leaving 4--8~GB for applications. A 3B model at Q4 requires ${\sim}2$~GB, comfortable for most flagship devices. (2)~\emph{Thermal}: Sustained inference on mobile \glspl{npu} is throttled by thermals; realistic sustained throughput is lower than peak throughput benchmarks suggest. (3)~\emph{Battery}: vendor guidance for mobile-targeted \glspl{slm} places per-prompt battery cost low enough to permit hundreds of interactions per charge, though published per-device figures remain scarce and are not reported under a common protocol. The fundamental constraint in edge deployment is memory bandwidth rather than compute: flagship mobile and laptop devices offer roughly 50--90~GB/s of memory bandwidth (single-board computers well under 30~GB/s) versus 2--3~TB/s for datacenter GPUs \citep{xu2024device}, making INT4 quantization not merely a storage optimization but a critical performance enabler.

\subsection{Edge and IoT Deployment}
\label{subsec:deployment_edge}

Below smartphone-class hardware lies a diverse ecosystem of edge devices: Raspberry Pi single-board computers, NVIDIA Jetson modules, and microcontrollers. \glspl{slm} targeting this tier typically require:

\begin{description}
    \item[Sub-1B or extreme quantization] A Raspberry Pi~5 (8~GB RAM, Cortex-A76 CPU) runs Q4-quantized 1B models at roughly ten tokens per second, with sub-500M models comfortably faster. Benchmarking shows that llamafile achieves up to $4\times$ higher throughput and 30--40\% lower power consumption than Ollama for equivalent models on single-board computers \citep{costa2025sbc}.

    \item[Jetson Orin] NVIDIA's Jetson Orin modules with TensorRT-LLM \citep{nvidia_tensorrt2024} serve quantized 3 to 7B models at interactive rates, with the larger-memory NX and AGX parts faster than the Orin Nano, enabling real-time local inference for industrial and robotics applications.

    \item[Microcontrollers (MCU)] Sub-100M models using aggressive quantization (INT4/INT2) can run on ARM Cortex-M series MCUs with 512~KB--2~MB SRAM for specialized tasks like keyword detection and sensor data analysis.
\end{description}

\subsection{Why the Deployment Gap Matters}
\label{subsec:deployment_latency}

The practical consequence of the preceding sections is a gap that is structural
rather than marginal. A quantized 3B model occupies roughly 2~GB of weight memory
and runs on hardware the user already owns, so the operator pays no per-query
charge for it and, subject to the scope conditions of
Section~\ref{subsec:deployment_privacy_scope}, the prompt is not transmitted to
an inference provider. A 70B model at FP16 needs roughly 140~GB, which places it
on multi-accelerator server hardware, and a frontier API model adds a network
round trip and a per-token charge to every call. Between those two conditions
there is little continuum for a given task: the small model is either adequate
for it or it is not, and where it is adequate the large model buys nothing that
the task can use.

Published cost estimates put the gap at one to two orders of magnitude.
\citet{belcak2025slm_agentic} estimate that serving a 7B \gls{slm} is 10 to
30$\times$ cheaper than serving a 70 to 175B \gls{llm} once latency, energy, and
FLOPs are accounted for. On the latency side, the binding constraint on edge
hardware is prefill rather than generation, because time-to-first-token dominates
perceived responsiveness in interactive use, and prefill cost scales with context
length. This is why \gls{gqa} and local-global attention interleaving, which cut
\gls{kv}-cache traffic, matter more for on-device deployment than for server
deployment.

\subsubsection{Calculated Quantities Versus Measured Ones}
\label{subsec:deployment_calc_vs_meas}

Because the distinction is easy to lose and consequential, we state which of the
quantities in this paper are computed and which would have to be measured.

\emph{Computed, and therefore reliable within their stated assumptions:} weight
memory at a given precision (Table~\ref{tab:memory_footprint}), which follows from
parameter count and bit-width; \gls{kv}-cache size per token, which follows from
the head configuration and context length; and the ratio between them. These are
arithmetic, and we present them as such.

\emph{Measured, and therefore dependent on conditions we do not control:}
throughput, time-to-first-token, sustained versus peak rates under thermal
load, energy per token, battery cost per interaction, and total cost of
ownership. Every one of these depends on batch size, context length, kernel
implementation, achieved memory-bandwidth utilization, driver and runtime
version, thermal envelope, and, for energy, the grid mix and the amortization
period assumed for device manufacture. Published figures for them are not
comparable across sources, and we do not tabulate per-scenario latency, energy,
or cost figures. Where a throughput figure appears in this paper it is attributed
to the source and the hardware it names (Table~\ref{tab:deployment_frameworks}),
and no cross-row comparison is drawn.

One claim in this family needs particular care, because it is widely repeated and
we have repeated it. Quantizing from 16 to 4 bits is often described as giving a
near-linear $4\times$ speedup. That holds under a specific regime: single-stream
autoregressive \emph{decoding}, at batch size~1, where the generation of each
token requires reading the full weight set and the hardware is
memory-bandwidth-bound rather than compute-bound. Outside that regime it does
not. Under batching, arithmetic intensity rises and the bottleneck shifts toward
compute, so the speedup shrinks. During prefill, which is compute-bound, it
largely disappears. On hardware without native low-precision kernels the
dequantization overhead can consume much of it. And the realized memory reduction
is itself $3.2$--$3.4\times$, not $4\times$, because mixed schemes retain
higher-precision tensors. The defensible statement is that 4-bit quantization
converts a storage saving into a decode-time saving in proportion to the
bandwidth it frees, and that on edge hardware in single-stream interactive use
this is the dominant regime.

Subject to all of this, the claim the argument of Section~\ref{sec:agentic}
actually needs is ordinal and robust: for a bounded, repetitive call that a small
model can complete correctly, the small model is cheaper by a wide margin, lower
in latency once the network hop is counted, and available offline.
